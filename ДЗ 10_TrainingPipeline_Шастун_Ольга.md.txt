# ДЗ 5: Автоматизоване тренування моделей: контроль процесу, ризики та production-readiness

## 1. High-level workflow automated training pipeline

Процес автоматизованого тренування моделі є керованим workflow, який забезпечує перехід від коду чи даних до готової моделі-кандидата через наступну послідовність етапів:

GitLab event / manual trigger ↓
GitLab CI pipeline
        ↓
AWS Step Functions execution
        ↓
Data validation
        ↓
Training job
        ↓
Model evaluation
        ↓
Logging metrics and artifacts
        ↓
Model Registry update 
        ↓
Notification to team

### Пояснення ключових елементів процесу:
- **Що запускає pipeline:** Подія в репозиторії (наприклад, push/merge у main), ручний запуск (manual trigger), розклад (schedule) або сигнал деградації якості (drift signal).
- **Яку роль виконує GitLab CI:** Виступає шар-тригером (trigger layer), який ініціює зовнішній процес, приймає параметри та передає Git-контекст (commit SHA, branch).
- **Яку роль виконує AWS Step Functions:** Працює як оркестратор workflow, керуючи послідовністю виконання задач в хмарі AWS.
- **Де фіксуються метрики:** Всистемі трекінгу експериментів MLflow.
- **Де зберігається модель-кандидат:** У Model Registry.
- **Хто отримує повідомлення про результат:** Команда (AI PM, MLOps, AI/ML Engineers) через інтегровані канали сповіщень.

## 2. Контрольні точки pipeline

| Етап pipeline | Що перевіряє команда | Хто owner | Що є успіхом | Що робити при помилці |
| :--- | :--- | :--- | :--- | :--- |
| **Data validation** | Наявність даних, схема, обов’язкові поля, відсутність критичних помилок | Data Engineer | Дані пройшли всі валідаційні перевірки | Зупинити pipeline, повідомити owner-а |
| **Training job** | Запуск тренування з правильною версією коду та вихідних даних | AI/ML Engineer | Training job успішно завершився | Перевірити логи, перезапустити або створити інцидент |
| **Model evaluation** | Якість метрик моделі та порівняння з поточним baseline | AI/ML Engineer + AI PM | Метрики моделі вище встановленого threshold | Не просувати модель далі, зафіксувати результат |
| **Logging** | Коректність фіксації метрик, параметрів та артефактів | MLOps Engineer | Усі дані експерименту залогізовані в системі | Перевірити систему трекінгу та права доступу |
| **Model Registry** | Статус моделі-кандидата та наявність тегів | MLOps Engineer | Модель зареєстрована як валідний кандидат | Перевірити статус реєстру / повторити логування |
| **Notification** | Доставка зрозумілого статусу виконання до команди | AI PM / MLOps Engineer | Команда отримала сповіщення з усіма деталями | Додати альтернативний alert або оновити runbook |

## 3. Quality gates для нової моделі

Перед тим як нова модель вважатиметься кандидатом на release та зможе просуватися далі в lifecycle, вона має пройти наступні перевірки:

| Quality gate | Приклад правила | Хто перевіряє | Рішення |
| :--- | :--- | :--- | :--- |
| **Data quality** | Немає критичних schema errors, пропущених обов'язкових полів та аномалій у даних | Data Engineer | Продовжити pipeline або зупинити при критичній помилці |
| **Model metric** | F1-score та Recall моделі не нижчі за встановлений production baseline (наприклад, F1 $\ge$ 0.82) | AI/ML Engineer | Просунути модель далі або відхилити (rejected) |
| **Business metric** | Відсутність погіршення метрик на критичних бізнес-сегментах користувачів | AI PM | Погодити бізнес-відповідність або повернути на доопрацювання |
| **Approval** | Модель успішно пройшла всі технічні перевірки та отримала статус approved | AI PM / Tech Lead | Надати офіційний дозвіл на розгортання у staging або production |

> **Увага:** Навіть якщо модель успішно навчилася технічно (technical success), вона не переходить у production автоматично без проходження цих quality gates та ручного approval від AI PM / Tech Lead.

## 4. Правила запуску training pipeline

| Trigger | Коли доречний | Перевага | Ризик | Рекомендоване середовище |
| :--- | :--- | :--- | :--- | :--- |
| **Push / Merge у main** | На етапі розробки та валідації архітектури pipeline | Простий автоматичний запуск кожної зміни | Створює зайві training runs і навантаження на інфраструктуру | dev |
| **Manual trigger** | Коли потрібен суворий контроль ресурсів або позаплановий ретренінг | Мінімізує випадкові запуск і зайві витрати хмари | Залежить від людського фактора та дисципліни команди | staging / production |
| **Schedule** | Для регулярно оновлюваних моделей за стабільним розкладом | Передбачуваність та автоматичне оновлення без участі інженера | Може запустити навчання за відсутності реальної потреби чи свіжих даних | staging / production |
| **Drift signal** | При реальному зниженні якості моделі або дрейфу даних (data/concept drift) | Запуск чітко за бізнес-необхідністю у відповідь на проблему | Потребує зрілої системи моніторингу і надійних метрик | production |

## 5. Risk register

| Ризик | Ймовірність (Likelihood) | Вплив (Impact) | Як зменшити ризик (Mitigation) | Owner |
| :--- | :--- | :--- | :--- | :--- |
| **1. GitLab CI має надмірні AWS-права** | Medium | High | Використання принципів найменших привілейостей (least privilege), OIDC-автентифікації та окремих IAM-ролей для dev/staging/prod. | DevOps / MLOps |
| **2. Модель не проходить quality gates** | Medium | High | Чітке порівняння з production baseline, встановлення фіксованих thresholds та обов'язковий manual approval. | AI/ML Engineer + AI PM |
| **3. Training запускається занадто часто** | High | Medium | Впровадження правил запуску за зміненими файлами (changed files), обмеження частих розкладів та ручні тригери. | AI PM |
| **4. Помилки валідації вхідних даних (Data drift / schema errors)** | High | High | Додавання окремого блоку валідації даних на початку pipeline із зупинкою процесу при критичних аномаліях. | Data Engineer |
| **5. Збій хмарної інфраструктури під час тренування** | Low | High | Налаштування автоматичного логування станів, таймаутів та сповіщень про збої у середовищі виконання. | MLOps Engineer |
| **6. Втрата артефактів або неможливість відтворити експеримент** | Medium | Medium | Обов'язкова фіксація всіх метрик, параметрів та коду в системі трекінгу (MLflow) та контроль версій датасетів. | AI/ML Engineer |
| **7. Несанкціонований або випадковий деплой моделі без перевірки** | Low | High | Технічне розмежування процесів тренування та релізу; повна заборона автоматичного переходу в production без ручного погодження. | AI PM / Tech Lead |


## 6. Acceptance criteria для Jira-задачі

Для задачі **«Інтегрувати GitLab CI з AWS Step Functions для automated training pipeline»** встановлені такі критерії прийняття (Acceptance Criteria):

- GitLab CI pipeline успішно ініціює та запускає AWS Step Functions workflow.
- У вхідних параметрах (input) Step Functions обов'язково передаються `commit SHA`, `branch` та `source = "gitlab-ci"`.
- Процес виконання (execution) повністю видимий та доступний для моніторингу в AWS Console.
- Pipeline містить окремий обов'язковий блок `data validation` перед запуском самого процесу тренування (`training job`).
- Результати навчання та метрики автоматично логуються в систему трекінгу (наприклад, MLflow).
- Усі ключові метрики і артефікати тренування доступні команді для перевірки.
- Нова модель успішно отримує відповідний статус у Model Registry (наприклад, `candidate`).
- Команда отримує автоматичне сповіщення (notification) про статус `success` або `failure`.
- Доступ GitLab CI до AWS налаштований за принципом найменших привілейостей без наявності зайвих (надмірних) прав.
- Перед просуванням моделі далі обов'язково перевіряються встановлені quality gates.
- Жодна нова модель не переходить у production автоматично без проходження ручного approval.



## 8. Короткий висновок

Автоматизований training pipeline є фундаментальним елементом зрілої MLOps-інфраструктури, оскільки він забезпечує відтворюваність, безперервність та системний контроль процесу навчання ML-моделей. У цій архітектурі GitLab CI виступає гнучким шаром-тригером (trigger layer), який передає Git-контекст та ініціює виконання зовнішніх процесів без прямого втручання в інфраструктуру. О оркестрацію безпосереднього виконання задач у хмарі бере на себе AWS Step Functions, що забезпечує надійне й прозоре управління послідовністю кроків. Важливо підкреслити, що технічно успішний запуск pipeline (technical success) свідчить лише про відсутність збоїв у виконанні коду, але не гарантує готовність моделі до експлуатації. Для досягнення справжньої production-readiness модель повинна пройти суворі quality gates, перевірку ML- та бізнес-метрики, а також отримати ручний approval від AI PM та Tech Lead. Такий багаторівневий підхід дозволяє мінімізувати інфраструктурні й бізнес-ризики та гарантує високу якість рішень у продакшені.



## 7. Notification messages

Система сповіщень надсилає автоматичні повідомлення в командний Slack-канал `#mlops-alerts` після завершення виконання пайплайну. Повідомлення містять повний контекст, щоб команда могла швидко зрозуміти статус, знайти необхідні деталі в логах та виконати наступну цільову дію.

### 1. Повідомлення при успішному виконанні (Success Notification)

```text
✅ Training pipeline completed successfully
• Pipeline Name: Automated Training Pipeline (churn_prediction_v3)
• Status: SUCCESS
• Source: GitLab CI
• Commit / Branch: a1b2c3d / main
• Key Metrics: F1-score = 0.83, Recall = 0.79, Precision = 0.86
• Status in Registry: candidate registered
• Details & Logs: MLflow Run #128 | AWS Step Functions Execution #step-4920
• Next Action: Tech Lead reviews quality gates before release decision
• Responsible / Owner: Tech Lead / AI PM

### 2. Повідомлення при помилці (Failure Notification)

• Status: FAILED
• Source: GitLab CI
• Commit / Branch: a1b2c3d / main
• Failed Step: DataValidation
• Reason: Missing required column customer_age
• Key Metrics: N/A (pipeline stopped at validation step)
• Details & Logs: Step Functions execution logs / GitLab job logs #8821
• Next Action: Data Engineer checks dataset schema and restarts pipeline after fix
• Responsible / Owner: Data Engineer
