# Аналіз ML-експериментів та перевірка готовності до Production (Iris Classification)

## 1. Бізнес-контекст ML-задачі

* **Задача моделі:** Класифікація сортів ірисів (Iris Dataset) на 3 класи (`setosa`, `versicolor`, `virginica`) на основі 4 ознак (довжина та ширина чашолистка та пелюстки). Загальний розмір вибірки — 150 квіток, розбиття: 70% train / 30% test (45 квіток).
* **Прийняття рішень:** Модель використовується для автоматичного визначення виду рослини у ботанічному/сільськогосподарському сервісі на основі фізичних вимірювань.
* **Кінцеві користувачі:** Польові дослідники, агрономи або клієнти ботанічного сервісу.
* **Критичність помилок (Business Trade-off):** Плутанина між видами може призвести до невірно обраного догляду або обробки рослин. Оцінка Log Loss показує впевненість моделі, що є критичним при автоматичному прийнятті рішень.
* **Ключові метрики:**
  * **Accuracy:** Частка правильно класифікованих квіток на тестовій вибірці (більше = краще).
  * **Loss (Log Loss):** Штрафує за неупевнені та помилкові передбачення (менше = краще).

## 3. Визначення кандидата на Staging / Production

**Обраний кандидат:** `rf-depth3` (`2ddc4f9d563c43e5a7c6c8523a580db3`)

### Обґрунтування вибору:
1. **Перевага за метриками:** Модель досягла найвищої точності **Accuracy = 0.9556** (95.56%) та найменшої помилки **Loss = 0.1415** серед усіх 5 експериментів.
2. **Порівняння з Baseline:** У порівнянні з `logreg-baseline` (Accuracy = 0.9333, Loss = 0.1913) прирост точності склав +2.23%, а Loss зменшився на 26%.
3. **Наявність Model Artifact:** Це **єдиний run**, для якого залогіновано повноцінний артефакт моделі (папка `model/` з файлами `MLmodel`, `model.skops`, `conda.yaml`, `requirements.txt`, `input_example.json`). Без артефакту фізичний деплой інших моделей неможливий.
4. **Відтворюваність:** Зафіксовано параметри `random_state=42`, `split_random_state=7`, `test_size=0.3`, що гарантує 100% відтворюваність результату.

## 4. Перевірка метрик у Grafana / Prometheus

### Результати аналізу моніторингу Prometheus:
* **`mlflow_accuracy`:** Значення повністю збігаються з MLflow UI (`rf-depth3`: ~0.9556, `rf-small`: ~0.9333, `logreg-baseline`: ~0.9333, `logreg-strong-reg`: ~0.8444, `decision-stump`: ~0.6667).
* **`mlflow_loss`:** Значення тотожні MLflow UI (`rf-depth3`: ~0.1415, `logreg-strong-reg`: ~0.6864).
* **Мітки (Labels):** Кожна метрика має мітки: `experiment`, `instance`, `job`, `model_type`, `run_id`, `run_name`.
* **Аномалії:** На графіках зафіксовано розрив близько 08:34 (UTC), викликаний перезапуском `mlflow-exporter`. На самі значення метрик це не вплинуло.

### Підсумок по інструментах:
* **Prometheus / Grafana показує:** Поточні метрики в реальному часі, історію експортера та стан доступності метрик.
* **MLflow UI показує:** Повний артефакт моделі, залежності (`requirements.txt`, `conda.yaml`), приклад входу (`input_example.json`) та гіперпараметри тренування.
* **Разом ці інструменти допомагають:** Забезпечити прозорий audit trail від навчання до моніторингу в runtime.
* **Але для production-рішення ще бракує:** Інфраструктурних метрик (Latency/Inference time, CPU/RAM) та аналізу Data Drift / Concept Drift у динаміці на реальному трафіку.

## 7. PM Decision Report

### Рекомендація:
**Go to Staging** (для кандидата `rf-depth3`).

### Обґрунтування:
Модель `rf-depth3` (`run_id: 2ddc4f9d`) показала найкращі результати серед усіх проведених експериментів, досягши **Accuracy 0.9556** та мінімального рівня втрат **Loss 0.1415**. Вона впевнено перевищує показники baseline.

### Основні докази:
1. Зафіксовано повний audit trail у MLflow (параметри, метрики, теги).
2. Наявність збереженого артефакту моделі (`model.skops`, `MLmodel`, `requirements.txt`), готового до деплою.
3. Метрики успішно верифіковані в системі Prometheus/Grafana.

### Основні ризики:
* Відсутність збережених артефактів у інших моделей, що унеможливлює швидкий rollback на альтернативні варіанти.
* Відсутність автоматизованих сповіщень на зсув даних (Data Drift).

### Що потрібно зробити перед Production:
1. Продеплоїти `rf-depth3` у **Staging-середовище** та провести заміри швидкості відгуку (Inference Latency).
2. Налаштувати автоматичне збереження артефактів для всіх майбутніх запусків у пайплайні тренування.
3. Підготувати Rollback-план та затвердити цільові thresholds для моніторингу в Grafana.
